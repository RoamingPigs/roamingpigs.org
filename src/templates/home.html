Speech models break down on radio-quality audio

{{ chip('measured') }}

Six open speech models transcribed {{ v.v2.n_utt }} synthetic radio calls through six audio paths at four noise levels: {{ v.v2.n_transcripts }} transcripts. Averaged over models and paths, word error was {{ v.v2.w['clean'].p }}% on clean audio (95% interval {{ v.v2.w['clean'].lo }} to {{ v.v2.w['clean'].hi }}) and {{ v.v2.w['0 dB'].p }}% at 0 dB ({{ v.v2.w['0 dB'].lo }} to {{ v.v2.w['0 dB'].hi }}). {{ v.v2.codecs_worse }} of the {{ v.v2.codecs_total }} narrowband paths were worse than uncompressed audio on clean speech, with intervals that exclude zero.{% if v.v2.any_over_100 %} Above 100% means the model wrote more wrong words than the call contained.{% endif %}

What this does not show

The speech is one synthetic voice at one speaking rate, not recorded radio, and the channel is simulated: noise is added after the codec, and the signal-to-noise ratio is measured over the whole clip including pauses. Every narrowband path also passes a 300 to 3400 Hz band-pass before coding, so a narrowband result combines band-limiting with the codec. The intervals cover the {{ v.v2.n_utt }} scripts, not other speakers, voices or phrasings. Scoring uses the Whisper English text normaliser, which was developed with those models. Results are for the Hugging Face library with greedy decoding on a CPU, and do not carry to other libraries, which apply extra thresholds by default. I did not test the five narrowband paths against each other, so I do not rank them. It says nothing about any product.

This run replaces a pilot published on 10 October that scored 5 calls on different audio and had decoding flaws, listed in the corrections.

Given silence, models still write words

{{ chip('measured') }}

On {{ v.v2.e1_n_distinct }} distinct clips of silence, static or radio squelch, each of six models returned text on {{ v.v2.e1_none }}% of them. Counting only text that contains a letter or digit, the rate was {{ v.v2.e1_strict_none }}% by model, because {{ v.v2.e1_punct_only }} outputs were only an ellipsis. {{ v.v2.gate_energy }} {{ v.v2.gate_neural }} Across models the energy gate left {{ v.v2.e1_energy }}% of clips with text, and the neural gate {{ v.v2.e1_neural }}%.

What a gate costs on speech, measured on {{ v.v2.speech_clips }} transcripts of clean and 0 dB speech: the energy gate changed word error by {{ v.v2.cost_energy }}, with {{ v.v2.energy_same }} transcripts unchanged. The neural gate raised it by {{ v.v2.cost_neural }}. Neither gate skipped a speech clip.

Where my written expectations were wrong

Before the run I wrote down that the energy gate would clear silence but not squelch, that the neural gate would clear more but not everything, and that either gate would cost something on speech. The energy gate also cleared the squelch bursts. The neural gate cleared every non-speech clip. The energy gate cost nothing here because the synthetic pauses are already digital silence and noisy clips never fall below its level threshold, so that result says nothing about real recordings. The neural gate was tested on generated noise, which may be easier to separate from speech than real noise. The full list.

What this does not show

The clips are 2.5 seconds of generated sound, ten seeds per condition, one setting for each gate. Real recordings may behave differently. A hallucination here means any word in the normalised output, which is a blunt definition: it does not separate a single stray word from a loop. The energy gate measures level only. The neural gate was tested as shipped, not tuned. Neither result applies to other models or to long recordings.

This replaces the 10 October pilot, which used 3 seeds and a different clip set.

Power/rate estimates from local inference summaries

{{ chip('modelled') }}

Dividing reported mean wall power by reported decode speed gives {{ v.j_min }} to {{ v.j_max }} joules per token for {{ v.n_runs }} local-model summaries. These are derived estimates, not meter readings of token energy. A separate calculated scenario gives {{ c.apu.calculated_9b.j_per_token }} for the smallest model; it is not an independently validated prediction. I have since measured this machine with a plan written first; the results, plan and raw power logs are public.

What this does not show

The summaries report {{ v.run_min }} to {{ v.run_max }} seconds and {{ v.run_tokens }} output tokens. The first summary separately reports integrated sample-window energy of {{ v.j_reported_first }} J/output token. That is a different estimator and window from the power/rate ratio; a similar peak-power ratio does not explain or replace it. Raw traces are absent, so the integrated value cannot be independently reconciled from this file. Do coordinated AI coding agents beat one agent?

{{ chip('measured') }}

On {{ c.echo.tasks }} small Python tasks, with {{ c.echo.attempts_per_arm }} attempts per arm, a single agent produced {{ c.echo.accepted.single }} accepted solutions. Ordinary two-worker messaging produced {{ c.echo.accepted.plain }}. Echo, the coordination layer I build, also produced {{ c.echo.accepted.echo }}, with Git merge conflicts in {{ c.echo.merge_conflicts.echo }} of {{ c.echo.attempts_per_arm }} attempts. No coordination benefit is established.

What this does not show

The tasks were reused and the agents may have seen them, so this is a diagnostic, not a benchmark. Transport timings measure messaging speed, not task success. The per-attempt file is derived: failure labels such as merge conflicts are mapped by rules from each attempt’s recorded status, the two “coders” are the same script so there is no inter-coder agreement to report, and per-attempt token counts are allocated from totals. The figures here are the summary counts. A coordination benefit would need fresh tasks and repeated runs.
