Speech models break down on radio-quality audio

{{ chip('measured') }}

Six open speech models transcribed five scripted maritime radio calls through six audio paths and five noise levels. Averaged over every path, word error was {{ v.wer_clean }}% with no added noise and {{ v.wer_0 }}% at 0 dB. Above 100% means the models wrote more wrong words than the call contained.

What this does not show

Five utterances is a pilot. The speech is synthetic (text to speech), not recorded radio traffic. There are no confidence intervals, so small gaps between codecs mean nothing yet. Decoding was greedy with a 48-token cap, and error above 100% includes inserted words. It says nothing about any product.

Given silence, every model still wrote words

{{ chip('measured') }}

On {{ c.e1.non_speech_clips_per_model }} clips of silence, static or radio squelch, each of {{ c.e1.models }} models wrote words on {{ c.e1.ungated_hallucinated_clips[0] }} of {{ c.e1.non_speech_clips_per_model }}. A basic energy gate removed the words on both silence conditions. It did nothing on any of the six noise and squelch conditions, so {{ c.e1.gated_hallucinated_clips[0] }} of {{ c.e1.non_speech_clips_per_model }} clips still produced text.

What this does not show

The clips are 2.5 seconds of generated audio, three seeds per condition, one gate setting (−42 dBFS). Real radio recordings may behave differently. The same models can be quiet with a better gate or a different decoder. Peak speed reached {{ v.e1_wpm_cell }} words per minute in one noise condition, which is a single cell, not a typical rate.

What a local model costs in energy, read off a wall meter

{{ chip('measured') }}{{ chip('modelled') }}

On one {{ v.apu_mem }} GB unified-memory machine, a wall meter read {{ v.j_min }} to {{ v.j_max }} joules per generated token across {{ v.n_runs }} models. Before I ran the meter, a calibrated model of mine had predicted {{ c.apu.calibrated_9b.j_per_token }} for the smallest. The meter read {{ v.j_first }}.

What this does not show

Each number is one run of {{ v.run_min }} to {{ v.run_max }} seconds and {{ v.run_tokens }} tokens. Energy per token uses mean wall power. Peak power gives higher values, up to {{ v.j_peak_first }} for the first run. This is one machine at batch size one. Serving many requests at once can lower energy per token several-fold, so this is not a comparison with data centre hardware.{% if v.excl %} A third run, on a {{ v.excl.params_b }}B mixture model, is left out. Do coordinated AI coding agents beat one agent?

{{ chip('measured') }}

On {{ c.echo.tasks }} small Python tasks, with {{ c.echo.attempts_per_arm }} attempts per arm, a single agent produced {{ c.echo.accepted.single }} accepted solutions. Ordinary two-worker messaging produced {{ c.echo.accepted.plain }}. Echo, the coordination layer I build, also produced {{ c.echo.accepted.echo }}, with Git merge conflicts in {{ c.echo.merge_conflicts.echo }} of {{ c.echo.attempts_per_arm }} attempts. No coordination benefit is established.

What this does not show

The tasks were reused and the agents may have seen them, so this is a diagnostic, not a benchmark. Transport timings measure messaging speed, not task success. A coordination benefit would need fresh tasks and repeated runs.
